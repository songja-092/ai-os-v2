- 상태: 회의 종료
- 기록 범위: PM1 완료 이후 PM2~PM4 설계 논의
- 원칙: 확정된 내용과 논의 중인 내용을 구분하며, 회의 종료 전까지 계속 갱신한다.

## 1. 현재 공식 상태

- PM1은 사용자 승인 완료 상태다.
- PM1 완료 Commit은 `75074311d2e5329d0b770765a95801c6a64f9ff0`이다.
- PM1 복구 태그는 `pm1-complete-2026-08-18`이다.
- PM1 잠금 파일은 PM2에서 수정하지 않는다.

- 기존 PM2 전체 화면 재구현 시도는 PM1 메뉴·기능·화면 구조를 손상시켰으므로 공식 결과로 사용하지 않는다.

## 2. PM 전환 자동화 — 확정

사용자가 완료된 PM마다 정답지를 직접 작성하지 않는다.

사용자가 `PM 통과`를 결정하면 V2/Codex가 다음을 수행한다.

1. 승인된 실행 화면과 주요 Screenshot 저장
2. 메뉴·버튼·핵심 상호작용 검사
3. 색상·글자·간격·Section ID 등 승인 기준 기록
4. 변경 가능 영역과 변경 금지 영역 기록
5. 이전 PM 기능 보존 여부 검사
6. Commit과 복구 태그 생성
7. 완료 PM 잠금
8. 다음 PM 전용 작업공간 생성
9. 다음 PM 진행 중 이전 PM과 자동 비교

자동 생성된 기준은 사용자가 `통과`한 뒤에만 공식 기준으로 승격한다. 테스트를 통과시키기 위해 승인 기준 Screenshot이나 잠금 기준을 임의로 갱신하지 않는다.

## 3. PM1 Golden Fixture — 방향 확정

PM1 자료는 단순 참고 이미지가 아니라 다음 PM이 지켜야 할 실행 가능한 기준본으로 사용한다.

현재 존재하는 기반:

- 실행 가능한 PM1 HTML
- PM1 완료 보고서
- Section ID 계약
- Commit·복구 태그
- 잠금 해시 검사

추가로 정리할 항목:

- 사용자 승인 Screenshot
- Design Token
- 핵심 상호작용 목록
- 변경 가능·금지 범위
- 다음 PM과의 시각·기능 비교 검사

PM1 Golden Fixture는 Core 상태나 제품 코드의 원본이 아니다. 사용자가 승인한 시각·상호작용을 보존하는 기준이다.

## 4. V2·프로젝트·Section·Module 정의 — 확정

### V2

V2는 Module이 아니다. V2는 제작 결과물을 장착하고 연결하는 보드판이다.

### 프로젝트

프로젝트는 사용자가 무엇을 만들지 관리하고 진행하는 작업공간이다. 프로젝트 자체를 Module이라고 부르지 않는다.

### Section

요구사항 대화, 현재 단계, 다음 행동, Preview 등은 프로젝트 작업공간을 구성하는 화면 영역이다. 이들을 Module이라고 부르지 않는다.

### Module

Module은 V2가 제작했거나 외부에서 가져와 검증한 실제 결과물이다. 웹사이트, 기능, 도구, 수집기, 영상 편집기, 3D Viewer 등 종류와 관계없이 V2 보드에 장착·제거·재사용할 수 있어야 한다.

예:

- 병원 웹사이트
- PDF 도면 기호 기능
- 예약 기능
- 견적 기능
- 자료 수집기
- 영상 편집기
- 3D Viewer
- 자동매매 기능

## 5. 현재 PM2 화면의 분류 — 확정

- 카톡형 요구사항 대화는 프로젝트 작업공간의 Section이다.
- 모바일 Preview Panel도 프로젝트 작업공간의 Section이다.
- `requirements-chat-v1`을 독립 Module로 부르지 않는다.
- 현재 대화 Fixture는 PM2의 Module 조립 성공 증거가 아니다.

## 6. PM2 Module 두 개 조건 — 수정 확정

현재 V2에는 보드에 장착·제거·재사용할 수 있도록 완성된 Module이 없다.

따라서 다음을 금지한다.

- 가짜 Module 두 개를 만들어 PM2를 통과시키는 것
- 기존 화면 Section을 Module이라고 바꿔 부르는 것
- Fixture를 실제 Module 검증 증거로 사용하는 것

PM2는 우선 Module을 받을 수 있는 보드판의 기반을 준비한다.

- Module 등록 규칙
- Module을 표시할 자리
- 켜기·끄기
- 제거
- 오류가 발생해도 V2 보드판 유지
- 이전 상태 복구
- Module이 없을 때의 정확한 빈 상태

빈 상태에서 제공할 진입점:

- `새 Module 제작`
- `기존 결과물을 Module로 전환`

실제 Module의 장착·제거·교체·재사용 검증은 실제 제작물이 생긴 뒤 수행한다.

## 7. PM2 통과 기준 분리 — 확정

### 현재 PM2에서 확인

V2 보드판이 미래의 Module을 안전하게 받을 수 있는 구조인지 확인한다.

### 실제 Module 제작 후 확인

- 실제 Module 등록
- 장착·제거·다시 활성화
- 다른 프로젝트에서 재사용
- Module 오류 격리
- 이전 배치 복구

실제 Module이 없는 현재 시점에는 두 번째 검증을 완료로 선언하지 않는다.

## 8. 외부 Skill 자동 연결 — 방향 확정

공식 사용자 표현은 `능력`이 아니라 `스킬`로 통일한다.

새 외부 Skill·Plugin·Library는 `V2 스킬 연결 관리자`가 다음 과정을 자동으로 수행한다.

1. 원본을 격리 폴더에 가져오기
2. 기능·출처·라이선스·외부 전송·필요 권한 확인
3. 기존 프로젝트 접근을 제한한 상태로 작동 시험
4. V2와 충돌하는 입력·출력 형식 확인
5. 원본을 직접 수정하지 않고 V2 연결 Adapter 초안 생성
6. 연결 전후의 시간·품질·오류·재작업 비교
7. 제거·복구 방법 생성
8. 사용자에게 `채택·보류·폐기` 결과 표시
9. 사용자가 채택한 경우에만 V2의 `스킬·기능` 영역에 연결

자동화할 수 있는 범위:

- 후보 가져오기
- 출처·라이선스 확인
- 위험 요소 검사
- 격리 실행
- 기존 방식과 비교
- Adapter 초안 생성
- 제거 방법 생성
- 결과 보고서 작성

사용자 승인이 필요한 범위:

- 채택·보류·폐기
- 실제 프로젝트 적용
- 기본 Skill 승격

용어 구분:

- Skill: V2가 작업할 때 사용하는 방법·도구
- Module: V2가 실제로 제작했거나 가져와 검증한 결과물
- V2 보드판: Skill을 이용해 Module을 제작·장착·관리하는 공간

외부 Skill 원본을 직접 수정하지 않는다. V2와 외부 Skill 사이에 제거 가능한 Adapter를 두며, Skill이 필요 없으면 Adapter와 연결 기록을 해제할 수 있어야 한다.

## 9. V2 Skill 보호 규칙 — 방향 확정

사용자의 최우선 조건은 완전 로컬 사용 자체가 아니라 V2와 사용자 프로젝트가 외부에 유출·도용·재학습·무단 재사용되지 않는 것이다.

기본 규칙:

- 비공개 프로젝트 원본 코드·문서·이미지를 외부 서비스에 자동 전송하지 않는다.
- V2 Core·Recipe·Run·설계 문서를 외부 서비스에 자동 전송하지 않는다.
- Secret·Token·Cookie·계정 정보는 Skill에 제공하지 않는다.
- 공개 웹 조사는 프로젝트 원본 대신 일반화된 검색어를 사용한다.
- 외부 전송이 필요한 Skill은 전송 대상·목적·보관 여부를 사용자에게 먼저 표시한다.
- 서비스 약관에서 학습 사용·보관·재사용 조건이 불명확하면 비공개 프로젝트 원본을 보내지 않는다.
- 필요한 경우 Screenshot 일부, 공개 자료, 가짜 데이터, 최소 코드 조각처럼 범위를 줄인 자료만 사용한다.
- 실제 프로젝트 수정은 격리된 복사본에서 먼저 수행하고 사용자 승인 후 반영한다.
- Skill 사용 종료 또는 폐기 시 해당 Skill의 권한과 임시 연결을 함께 제거한다.
- 외부에서 가져온 코드·이미지·디자인도 출처와 라이선스를 확인해 타인의 자료를 무단 도용하지 않는다.

사용자는 복잡한 설정 대신 필요할 때 다음 중 하나를 선택한다.

- `이번만 허용`
- `이 프로젝트에서 허용`
- `취소`

V2와 사용자 프로젝트가 외부로 넘어가지 않는 것이 확인된 로컬·오픈소스 Skill은 자동 격리 시험 대상이 될 수 있다. 외부 서비스 연결은 같은 수준의 보호가 확인되거나 사용자가 전송 내용을 명시적으로 승인한 경우에만 사용한다.

## 10. Skill 채택·보류·폐기 기준 — 확정

`V2 스킬 연결 관리자`는 새 Skill을 기존 Skill과 먼저 비교한다.

확인 항목:

- 기존 Skill과 겹치는 기능
- 새로 추가되는 기능
- 기존 방식보다 시간·품질·오류·재작업이 좋아지는지
- 현재 사용할 프로젝트나 작업이 있는지
- 안전하게 연결 해제·복구할 수 있는지
- 비용·외부 전송·라이선스 문제가 없는지

판정:

- 채택: 지금 가치가 있고 기존 방식보다 낫거나 새로운 일을 하며 안전하게 제거할 수 있음
- 보류: 가치가 있지만 현재 사용처가 없거나 비교·보안·비용 확인이 더 필요함
- 폐기: 중복인데 이점이 없거나 품질·안전·비용·복구 조건을 통과하지 못함

## 11. 채택 즉시 기본 Skill 적용 — 확정

사용자가 `채택`을 선택하면 별도의 승격 승인 단계를 반복하지 않는다.

채택 즉시:

1. V2 기본 Skill 목록에 등록
2. 승인된 사용 범위에서 활성화
3. 해당 작업부터 바로 사용
4. 사용한 Skill 이름·Version·Adapter 기록
5. 이전 Skill과 설정은 즉시 삭제하지 않고 복구 지점으로 보존

채택 후 실제 사용에서 문제가 생기면 해당 Skill을 비활성화하고 이전 Skill·Version으로 즉시 복구할 수 있어야 한다. 채택은 즉시 적용을 의미하지만 복구 가능성과 사용 기록은 유지한다.

## 12. 수집기 실행 순서 — 확정

사용자가 새로운 작업을 입력하면 수집기는 항상 시작한다. 다만 처음부터 외부 웹을 대량 조사하지 않는다.

실행 순서:

1. 사용자 요청 확인
2. 현재 프로젝트의 파일·결정·과거 성공 결과 확인
3. V2에 채택된 기존 Skill·Recipe·Block 확인
4. 기존 자료로 해결 가능한 부분과 부족한 부분 구분
5. 부족한 부분만 공개 웹·GitHub·공식 문서 등 외부 조사
6. 기존 방식 재사용안과 새 후보를 함께 사용자에게 표시
7. 사용자가 선택한 뒤 제작 시작

수집기는 매 요청마다 작동하지만 내부 자료 확인과 외부 조사를 단계로 분리한다. 기존 Skill과 파일을 확인하지 않고 같은 자료를 반복 수집하지 않는다. 외부 조사 결과도 자동 채택하지 않으며 출처·라이선스·보안 조건을 확인한 후보만 보여준다.

## 13. 회의 종료 판정

현재 PM2 진행 전에 꼭 필요한 결정은 완료됐다.

확정:

- PM 통과 시 Golden Fixture·회귀검사·Commit·Tag·잠금을 자동 준비
- V2·프로젝트·Section·Skill·Module 용어 구분
- 실제 Module이 없는 상태에서 가짜 Module 두 개를 만들지 않음
- PM2는 먼저 Module을 받을 수 있는 보드판 기반과 정확한 빈 상태를 준비
- 외부 Skill은 `V2 스킬 연결 관리자`가 격리 시험·중복 비교·Adapter·제거 경로를 준비
- 사용자 채택 즉시 기본 Skill로 적용하고 이전 Version은 복구용으로 보존
- V2와 비공개 프로젝트의 외부 유출·도용·재학습 방지
- 모든 요청에서 수집기는 내부 파일·기존 Skill·Recipe를 먼저 확인하고 부족한 부분만 외부 조사
- 사용자가 결정해야 할 새 설계·범위·비용·보안 문제가 생기면 Codex가 별도 회의를 요청

지금 결정하지 않아도 PM2 진행을 막지 않는 항목은 보류한다.

- 실제 Module이 생긴 뒤 장착·제거·재사용 검증
- PM3 외부 편집 도구 선택
- 자식 보드·업종별 Pack의 구체적인 판매 방식
- 반복 실패를 이용한 Skill 자동 개선의 상세 구현

위 항목은 실제 필요가 생겼을 때만 회의를 다시 연다.

향후 필요할 때 논의할 항목:

- Registry와 Manifest의 실제 사용자 친화적 표현
- Module 상태와 프로젝트 상태의 저장 방식
- 내부 Module과 외부 미검증 도구의 격리 수준
- PM3 외부 편집 도구 후보
- 자식 보드·상업화 구조
- Skill 반자동 개선 구조
