# AI OS V2 엔지니어링 운영 모델

이 문서는 AI OS V2를 어떤 방식으로 조사·제작·검증·자동화할지 정하는 통합 원본입니다.
Codex·Antigravity·기타 AI는 새 세션에서 `SESSION_START_CONTRACT.md`를 읽은 뒤 이 문서를 함께 확인합니다.

## 현재 공식 방향

현재 기본 방향은 **Harness-first, Spec-guided, Eval-driven, Human-approved, Loop-assisted**입니다. 짧게는 **Harness-first, Loop-ready**라고 부릅니다.

- `Harness Engineering (하네스 엔지니어링)`: 사람이 목표·범위·승인·안전장치를 정하고, AI가 그 안에서 작업하도록 환경·도구·증거·복구 절차를 설계합니다.
- `Loop Engineering (루프 엔지니어링)`: 반복 가능하고 판정 가능한 작업만 자동 실행·검사·수정·재검사합니다.
- V2는 하네스를 기본으로 유지하고, 실제 병목이 반복될 때만 제한된 자동화 루프를 추가합니다.
- 초기 비교 조사는 완료했으며 이 조합이 현재 V2에 가장 적합한 기본 구조라고 판정했습니다. 업계의 절대적 최선이라는 주장과 실제 프로젝트 반복 효과는 아직 검증하지 않았습니다.

## 2026-09-02 공통 작업 방식 최신화

모든 Codex 세션·전담 세션·웹 GPT·Antigravity는 다음 순서를 공통 기본값으로 사용합니다.

```text
초반 통합 인터뷰·기존 답 재사용
→ 목표·금지·완료·중단 조건을 실행 계약으로 고정
→ 저장소·잠금·기존 성공 Recipe 확인
→ 조사·Reference·후보 비교
→ 격리 Pilot
→ 기계적 기술 검사
→ 총괄의 Result-first 실제 결과 품질 검사
→ 허용된 자동 수정·재검사 Loop
→ 전체 회귀·복구 검사
→ 사용자 최종 선택·승인
→ Commit·Version·Restore·GitHub·Obsidian 동기화
```

- 사용자 개입은 원칙적으로 초반 통합 인터뷰와 마지막 최종 승인에 둡니다.
- 로그인·권한·비용·개인정보 외부 전송·도메인·외부 공개·파괴적 변경은 실행 직전에 추가 확인합니다.
- Build·Schema·Fixture PASS는 결과 품질 PASS가 아닙니다.
- 전담 Agent의 인수인계는 실행 명세이며 목표 화면, 숨길 내부 정보, 보존 범위, 도구 역할, PASS, FAIL, 즉시 중단, 보고 경계를 모두 포함해야 합니다.
- 총괄 Agent가 실제 결과를 직접 확인하기 전 다음 단계·Core 승격·Commit·Push를 금지합니다.
- 사용자가 만족하지 않은 결과는 기술적으로 작동해도 실패 Pilot로 분리하고 기존 공식 흐름에 전파하지 않습니다.

## 변하지 않는 목적

> 초보자가 AI와 검증된 도구를 사용해 전문가 수준 결과물을 안전하게 제작·수정·검증·복구할 수 있게 합니다.

목적은 유지하지만 Skill·MCP·편집기·수집기·구현 Agent·검사 도구는 더 나은 것이 확인되면 교체할 수 있습니다.

## 바꿀 수 없는 안전 계약

- 직접 확인하지 않은 기능·PASS·동기화·복구를 됐다고 말하지 않습니다.
- 사용자 승인, 개인정보·프로젝트 비공개, 작업 범위 잠금, 증거 보존을 생략하지 않습니다.
- 기존 PM 잠금·Commit·Artifact를 새 방식 시험 때문에 무효화하지 않습니다.
- 제품 적용 전 격리 시험과 복구 경로를 확인합니다.
- 자동화가 실패하거나 효과가 없으면 수동 흐름으로 돌아갈 수 있어야 합니다.
- 사용자는 채택·보류·폐기와 최종 승인 권한을 가집니다.

## 교체 가능한 영역

- Skill
- MCP
- Plugin·Adapter
- 편집기
- Reference 수집기·분석기
- 구현 Agent
- 품질 검사 도구
- 디자인 공급원

교체 가능한 도구가 Core 상태·승인·Version·Restore의 공식 원본을 소유하면 안 됩니다.

## 방법을 도입하는 표준 흐름

```text
V2 목적·안전 원칙 고정
→ 현재 성능 기준 기록
→ 반복되는 실제 병목 확인
→ 공식 문서·GitHub·Reddit·YouTube 조사
→ 안정 기본값·격리 시험·관찰 후보로 분류
→ 격리 Pilot
→ 기존 방식과 같은 조건으로 비교
→ 사용자 채택·보류·폐기
→ 제한된 자동화 루프
→ 실제 프로젝트 적용
→ 효과 측정
→ 효과가 없으면 제거
→ 여러 프로젝트에서 반복 성공하면 기본값 승격
```

유행이나 V2의 기존 결론을 정당화하기 위해 조사하지 않습니다. 현재 V2를 목표로 끌고 갈 수 있는 방법을 찾고, 반대 증거와 실패 사례도 함께 기록합니다.

## 근거를 구분하는 법

| 출처 | 확인할 내용 | 단독 채택 가능 여부 |
|---|---|---|
| 공식 문서·논문 | 기능·계약·연구 결과 | 실제 V2 효과는 별도 검증 필요 |
| GitHub | 코드·License·Release·유지관리 | 별 수만으로 채택 금지 |
| Reddit·YouTube | 실제 사용 장단점·실패 사례 | 홍보·개인 경험과 사실 구분 |
| V2 격리 Pilot | 설치·실행·효과·제거·복구 | 사용자 판정 전 승격 금지 |
| 실제 프로젝트 | 시간·품질·재작업·회귀·복구 | 반복 성공 전 기본값 확정 금지 |

## 자동화 전 성능 기준

방법을 바꾸기 전에 가능한 범위에서 다음을 기록합니다.

- 제작 소요 시간
- 사용자 개입 횟수
- 수정 요청 횟수
- 회귀 오류 수
- Token·도구 사용량
- 사용자 디자인 만족도
- 자동검사 PASS 비율
- Restore 성공 여부

기준이 없으면 “좋아졌다”를 공식 결과로 판정하지 않습니다.

## 자동화할 수 있는 조건

다음 조건을 모두 만족하는 작업만 Loop 후보입니다.

- 같은 형태로 반복됩니다.
- 입력과 출력이 명확합니다.
- 기계적으로 PASS·FAIL을 판정할 수 있습니다.
- 실패해도 복구할 수 있습니다.
- 시간·비용·시도 횟수 제한을 둘 수 있습니다.
- 중단과 사용자 호출 조건이 명확합니다.

```yaml
bounded_loop:
  max_attempts:
  time_or_cost_limit:
  pass_condition:
  stop_condition:
  rollback_method:
  human_escalation:
```

디자인 취향, 범위·가격 결정, 외부 공개, 최종 채택처럼 사람의 판단이 필요한 작업은 자동 승인하지 않습니다.

일반 오류 수정 Loop는 사용자 호출 없이 이어가되 다음 Barricade에서 즉시 멈춥니다.

- 목표·완료·중단 조건 불명확
- 승인 범위 확대 또는 잠금·Dirty 충돌
- 실제 결과 품질 Gate 실패
- 사용자 선택 전 선택 의존 구현
- 비용·로그인·외부 전송·공개·파괴적 변경 필요
- 도구 역할·License·제거·Restore 경계 미확인
- 총괄이 Runtime 또는 결과물을 직접 검증할 수 없음

## 자동화 제거 계약

자동화는 다음 순서로 완전히 제거할 수 있어야 합니다.

```text
Loop 비활성화
→ 기존 수동 Workflow로 전환
→ Recipe·Artifact·승인 기록 보존
→ Package·설정·Adapter 연결 제거
→ Build·회귀·Restore 검사
```

도구 전용 데이터만 남아 수동 흐름이나 Core가 작동하지 않는 구조는 채택하지 않습니다.

## 조사·자동화 시작 조건

상시 유행 감시나 모든 요청의 대규모 수집은 하지 않습니다. 다음 중 하나가 발생하면 조사 또는 자동화를 시작합니다.

- 같은 문제가 3회 이상 반복됩니다.
- 작업 시간이 정한 기준을 반복해서 넘습니다.
- 같은 수정 요청이나 회귀 오류가 반복됩니다.
- 기존 Skill·도구로 해결할 수 없는 기능이 필요합니다.
- 채택한 도구가 유지되지 않거나 보안·License 위험이 생깁니다.
- 새로운 프로젝트 유형이 현재 제작 능력 밖입니다.

## 방법 상태

모든 방법과 도구는 다음 세 상태 중 하나로 관리합니다.

- `stable_default`: 반복 성공과 복구가 확인된 기본 방법
- `isolated_trial`: 격리 시험 중이며 제품 기본 흐름에 미포함
- `watchlist`: 조사만 했거나 도입 근거가 부족한 후보

승격 순서는 `조사 → 격리 시험 → 기존 방식 비교 → 사용자 채택 → 실제 프로젝트 → 반복 성공 → stable_default`입니다.
