# AI OS V2 Constitution

## Core Principles

### I. 사용자 의도 우선

사용자는 자연어로 원하는 결과를 설명하고 선택·수정 요청·최종 승인에 집중해야 한다.
기술 선택과 구현 세부사항은 사용자의 목적을 바꾸지 않는 범위에서 AI가 정리해야 한다.
모호한 요구사항은 구현 전에 명세로 구체화해야 한다.

### II. 조립 우선

새 기능은 검증된 기존 도구, 오픈소스, Skill, MCP와 서비스를 먼저 조사하고 실제로
검증한 뒤 채택해야 한다. 적합한 대안이 없을 때만 부족한 연결부를 최소 구현한다.
이미 존재하는 기능을 V2 전용 코드로 중복 제작해서는 안 된다.

### III. 상태와 증거 분리

모든 작업은 `💡 제안`, `📝 승인됨`, `🔨 구현됨`, `✅ 검증됨` 상태를 구분해야 한다.
코드나 설정이 없으면 구현됐다고 표현해서는 안 되며, 실제 동작 증거가 없으면
PASS·완료·검증됨으로 표현해서는 안 된다. 확인하지 못한 내용은 `확인 필요`로 기록한다.

### IV. 공식 기억 단일화

GitHub `main`의 승인된 Commit을 공식 원본으로 사용해야 한다. Wiki는 사람이 읽고
편집하는 장기 기억이며, Archify와 기타 시각화는 특정 Commit에서 생성된 파생 자료다.
AI는 작업 시작 전에 실제 저장소의 최신 확정 Wiki를 읽고 채팅 기억보다 우선해야 한다.

### V. 안전한 변경과 복구

외부 도구나 기능 도입 전에는 현재 검증 상태를 Commit 또는 태그로 고정해야 한다.
변경은 별도 시험 브랜치에서 수행하고 실제 검증 후에만 `main` 반영 후보가 된다.
실패한 시험은 공식 상태로 합치지 않으며 복구 기준 Commit을 항상 보고해야 한다.

## 작업 범위

- 기능 명세는 무엇과 왜를 먼저 정의하고 기술 구현은 계획 단계에서 결정한다.
- 사용자 승인 없이 아직 확정되지 않은 Kernel, Planner, Multi-Agent 또는 V2 UI를
  구현된 구조로 취급하지 않는다.
- 비밀정보, Token, API Key와 개인 데이터는 Git에 포함하지 않는다.
- 한 작업은 가능한 하나의 의미 있는 변경과 검증 결과로 제한한다.

## 개발 흐름

기본 흐름은 `Specify → Clarify → Plan → Tasks → Analyze → Implement → Converge`다.
구현이 끝나면 실제 테스트와 사용자 확인을 거친 뒤 Wiki 반영, Commit, Push 순서로
공식 기억을 갱신한다. 구현 Agent의 완료 보고만으로 검증을 대신해서는 안 된다.

## Governance

이 Constitution은 Spec Kit이 생성하는 모든 명세·계획·작업보다 우선한다. 원칙 변경은
사용자 승인과 변경 이유를 기록해야 하며 Semantic Versioning으로 버전을 갱신한다.
각 Spec과 Plan은 조립 우선, 상태 구분, 증거, 복구 가능성을 명시적으로 확인해야 한다.
